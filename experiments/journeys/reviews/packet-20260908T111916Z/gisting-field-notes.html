The whole report in one minute

  1. Every time a coding agent asks its model to do anything, it first sends a long preamble: rules of behaviour plus a catalogue of every tool. The model rereads it on every turn.
  2. Shopify replaced their preamble with a few thousand learned made-up words and cut latency 38 percent. We asked whether that works for Claude Code driving a model we host ourselves.
  3. We measured first. On short sessions, 73 percent of what the model reads is preamble, and almost all of it is the tool catalogue, not the rules.
  4. We proved the model can accept 4,386 new words in its dictionary without ever saying them.
  5. We collected 126 real coding sessions. The preamble's share falls with depth: 0.72 early, 0.44 over a long session, 0.18 at the deepest turns.
  6. We recorded the full-preamble model's opinions once (the teacher), then trained only the made-up words to reproduce them (the student). One epoch, four hours.
  7. We gave Claude Code twelve checkable coding jobs with each preamble. Twelve of twelve both ways, reading 13,000 fewer tokens per turn with the made-up words.
  8. One blemish: in 84 tool calls the student once named a tool that does not exist. The catalogue's edge is where compression is weakest.
  9. Then we let the loop run itself: three boxes, three shorter summaries (2:1, 8:1, 16:1), no human step from training to destruction. Twelve of twelve at every ratio, zero invented tool names. Even 1,099 made-up words for the 17,539-token preamble held on this task set.
  10. Then a harder exam, sixteen tasks that need rare tools, real repositories, rule-keeping, and resistance to a booby-trapped file. Every compressed model dropped to 11 or 12 of 16 against the teacher's 15, and the failures were all one defect: they wrote results to invented directories, because the working-directory path, session id included, had been compressed into the summary.
  11. The rule that fixes it: anything that must be reproduced verbatim, paths, ids, dates, names, stays outside the gist. Retrained with that rule, the 8:1 model scored 16 of 16, equal to the teacher the same night.
  12. Finally the clean speed test, both arms with caching on. For one session at a time the gist saves almost nothing, because on this model the reading is not where the time goes. Under load it delivers 16 percent more requests per minute and cuts the slow tail of first-token wait by 39 percent. Shopify's throughput gain reproduces; their latency gain does not, exactly as the architecture predicted.
  13. Two more recipes through the loop. Averaging the training loss per response rather than per batch cost one task and a fifth more error, as Shopify reported, mildly. And a week of practice with the rarely used tools did not help: with or without 299 targeted examples, the 8:1 summary reaches for those tools about 60 percent of the time the full handbook does. That is a limit of the summary's size, not of the data.
  14. Total spend $105. Every failure along the way was plumbing or the provider, not the method; the surprises ledger lists all twenty-two, and the loop healed five of them on its own.

Lesson 1 · the idea

A note the contractor rereads before every sentence

Everyday anchorImagine hiring a contractor who, before saying anything, rereads the whole employee handbook and the complete catalogue of tools in the van. Every sentence. If you could hand them a one-page summary that produced exactly the same behaviour, you would.

A language model does not read words. Text is chopped into tokens (word pieces), and each token is looked up in a table that turns it into a list of numbers, its embedding. The model only ever consumes those number lists. Gisting is the observation that nothing forces the table to contain only real words. You can add rows for invented tokens, and choose their numbers so that a few thousand of them carry the same meaning as the twenty thousand real ones they replace.

Assumption exposed"The prompt is fixed text; the only way to make it cheaper is to write less of it." The table is the doorway between text and model, and the doorway can be widened.
The pointGisting is not a new model. It is 4,386 new rows in a lookup table, trained so that the model behaves identically with either preamble in front of it.
Depth: how the rows are chosen, and why the model is frozen

You cannot write the numbers by hand. You set up a matching game. Run the model with the full preamble on a real conversation and record, at every position of its reply, its full list of next-token probabilities. That is the teacher. Run the same model with the gist rows in place of the preamble and record the same lists. That is the student. Score the disagreement with KL divergence (a standard single number for how different two probability lists are), then nudge the gist rows in the direction that shrinks it, over thousands of conversations. Distillation is the name for training by copying outputs; self-distillation because teacher and student are the same network with different inputs.

All other weights stay frozen. Two payoffs: the model cannot drift anywhere else, and the deliverable is not a new model but a few thousand extra table rows plus a tokenizer entry per row, which any serving stack already understands.

new terms: token · embedding · teacher · student · KL divergence · self-distillation

Lesson 2 · the harness

What Claude Code actually sends, and why we tapped the wire

Everyday anchorBefore renovating a kitchen you photograph it. Not because you distrust the plans, but because the plans show what someone thought was there, and the photo shows what is.

Claude Code is a coding agent: a program that reads your repository, edits files, runs tests, and asks a language model what to do next at every step. Each step is a request containing the rules, the tool catalogue, the whole conversation so far, and the model's reply. We could not compress what we had not seen, so the first thing built was a tap: a 230-line proxy between Claude Code and the model that forwards every request unchanged and writes it to a log with timing.

Assumption exposed"The system prompt is the thing to compress." The rules are 1,500 tokens. The tool catalogue is 16,000. Two thirds of the catalogue describes tools the sessions never used.
The pointThe tap is the most valuable component in the program. It is the measurement instrument, the place where the swap happens, and the A/B switch, and Claude Code never has to change.
Depth: the anatomy of a request, and what counts as static

Claude Code speaks the Anthropic Messages API. vLLM, the serving engine, implements that API natively, so pointing Claude Code at it needs one environment variable. The engine folds the tool catalogue into the system message through a chat template (a script that lays the conversation out as one text stream) and puts the tool block before the instruction text, after a one-line reasoning-effort preamble.

Static means byte-identical across sessions after that template renders it. We found the static span by diffing system texts across sessions. What varies: the working-directory path, the git branch and status block, the date, and the served model's name, which Claude Code writes into its own prompt. Everything else, 17,540 tokens for the trimmed catalogue, is identical.

stack
tap: proxy/tap.py, stdlib only, streams SSE through and reassembles the reply serving: vllm/vllm-openai:v0.28.0, --language-model-only, prefix caching on, --max-num-seqs 64 client: claude 2.1.259, auto-update off, attribution hash off (it changes the prompt per request)
incidents

Claude Code requests reasoning effort "high"; Qwen3.8 accepts only xhigh, medium, low and returned 400 on every turn until the tap remapped it. In print mode Claude Code reads stdin, so a shell loop feeding it a task list appended the rest of the list to the first prompt. Both are recorded in the surprises ledger.

new terms: coding agent · Messages API · chat template · static span

Lesson 3 · the measurement (E0)

Is the note big enough to be worth summarising?

Everyday anchorYou would not hire someone to shorten a two-line memo. You would to shorten a forty-page one that everyone must read every morning.

Depth: how the share was counted exactly

The share is the static span divided by the tokens the model actually read on a turn, averaged over a session. Local tokenizer counts undercount because the chat template reformats the tool JSON, so the analyzer sends the system text plus tools through the engine's own tokenize endpoint and subtracts a bare user turn. Context per turn comes from the engine's reported input token count.

Prefix caching is the free competitor: the engine remembers the computation for a prefix it has seen before. It works on this hybrid model, in "align" mode for the state-space layers. Gisting must beat the cached case, not the uncached one.

incidents

The engine's default of 1,024 concurrent sequences exceeds the 674 state-space cache blocks that fit on 96 GB and aborts startup. The first launch stalled on an in-loader download; the second lost its engine when a tmux server vanished; a kill command matched its own shell and killed the command instead. Three launches to one working server, all logged.

Lesson 4 · the dictionary (section 3.3)

Can this model accept made-up words without saying them?

Everyday anchorAdding a private shorthand to a shared dictionary is safe only if nobody starts using it in public. The test is not whether the word can be looked up. It is whether it ever comes out of someone's mouth.

Two things could block the method before any training. The serving engine might refuse a model whose lookup table has grown. Or the model might start writing the new tokens in its answers, since a grown output side gives them a vote. This model had 243 spare rows, nowhere near 4,386, so the table had to be enlarged.

Assumption exposed"Adding tokens is a tokenizer change." It is two tables, input and output, and they are not tied in this model. Grow the input, and leave the output rows at zero so a gist id can never win a vote.
The pointDone on a laptop with no GPU, from a 2.5 GB slice of the checkpoint. The engine loaded the grown model on the first try and never emitted a gist id in thirty generations across three journeys.

Lesson 5 · real sessions (E1, coverage)

What the note is worth when the work gets long

Everyday anchorA fixed-size preface is most of a short letter and a footnote in a long one. The letter grows; the preface does not.

Toy sessions flatter the share. We ran 126 sessions on three real open-source repositories, some thirty minutes long with forty-turn caps, through the same tap against the full-prompt model. This is also the training data for everything after.

A shell driver ran Claude Code headless, one session per task line, each in a fresh copy of the repository, with an allowlist of tools rather than blanket permission. Lesson 6 · the teacher

Recording the expert's opinions once

Everyday anchorAn examiner writes the model answers once and files them. Every student paper after that is marked against the file, not by asking the examiner to redo the exam each time.

The teacher is the same model reading the full preamble. Its opinion of the next token, at every position of every logged reply, is the target the student must match. Computing it costs a full 33,000-token pass per example, and the plan's first training design paid that cost on every training step. Shopify's single biggest speed-up was to pay it once and file the result.

Assumption exposed"Training needs the whole distribution over 252,000 tokens." The top 32 candidates carry 0.999 of the probability mass on average and at the tenth percentile. The file is 54 MB.
The pointThe cache is what makes a research loop affordable. With it, one recipe costs one student pass over the data, about four hours here, and the teacher file is reused for every recipe that keeps the same span.
Depth: how the teacher was recorded, and what nearly broke

vLLM's completions endpoint accepts prompt_logprobs=K and returns, for every prompt position, the top-K tokens with log-probabilities. We sent each example as teacher prefix plus response and kept the last positions. The engine computes full-vocabulary log-probabilities per prefill chunk: an 8,192-token chunk times 252,544 vocabulary times 4 bytes is 8 GB, which killed the engine at 92 percent memory utilization. It ran at 80 percent with 4,096-token chunks, leaving a 350,278-token KV pool.

The KL is taken against the teacher's top-32 renormalised to sum to one; the student's log-probabilities are gathered at those 32 ids. The examples are sorted by session and turn so the prefix cache serves consecutive turns.

Lesson 7 · the student

Teaching 4,386 words to mean the same thing

Everyday anchorLearning a colleague's shorthand: you guess what each squiggle means, check against what they actually wrote, and adjust. You are not changing the colleague. You are changing your reading of the squiggles.

Training touches exactly one tensor: 4,386 rows by 5,120 numbers, 22 million values, against a model of 27 billion that stay frozen. On each step the student reads the gist prefix plus a logged reply, its next-token guesses are compared with the filed teacher opinions, and the rows move a little toward agreement.

Assumption exposed"How you average the loss is a detail." Shopify found per-response averaging made the model hallucinate and batch-level averaging did not. We used batch-level from the start and instrumented by turn length; the ablation itself is still on the queue.

Depth: the trainer, and the two failures that were ours

A forward hook on the input embedding replaces the output rows for any id at or above the first gist id with the trainable tensor, so the frozen table is never edited during training. Loss at response positions only: the hidden states for the last R positions go through the output head, and KL is computed there. Gradient checkpointing keeps a 30k-token sequence within 96 GB, at the price of recomputing activations in the backward pass.

incidents

First run: out of memory on the student pass. The library's checkpointing only engages in training mode and the model was in eval mode, so every activation was kept. One line fixed it. The pipeline-gate run in journey 2 used 50 examples with the live teacher, 32 seconds per example, and cut KL from 0.66 to 0.47 on a full-vocabulary measure; that scale is not comparable with the top-32 numbers above.

Lesson 8 · the swap and the exam (E2)

Same jobs, two preambles, one marking scheme

Everyday anchorTwo contractors who are the same person with two different handbooks, given the same twelve jobs and the same inspector. Not a survey of how they felt about it. Did the work pass inspection.

Serving the gist to Claude Code needed two pieces and no change to Claude Code. The tap, in gist mode, finds three anchor segments in the incoming instruction text, swaps each for its gist string, and prepends the tool-block gist. A conditional chat template on the server skips rendering the tool block when it sees gist tokens, while the request still carries the tools so the engine's tool-call parser stays active. Both arms then ran on the same server, since the gisted checkpoint has identical weights for every real token.

Depth: the evaluation protocol, and the two caveats in the table
protocol

Twelve tasks on a two-file seed repository with a deliberately failing test: add a function and a test, make an empty-list case return zero, create a module with tests, add type hints, add a clamp, change an error type with a message, add a power function with a negative-exponent test, explain without editing, write a README naming every function, report the failing test without editing, add a parity function, create a flatten utility. Each has a checker that inspects the files and runs the relevant tests. Four concurrent sessions, twenty-turn cap, tool allowlist, MCP servers excluded so the catalogue is the 27 built-in tools.

caveats

Latency is confounded: the teacher arm ran while the teacher-cache job was saturating the same server's CPU, so 23.8 seconds overstates the gap. The proper speed measurement is still owed, and lesson 9 explains why the ceiling is lower on this model than Shopify's. The one invented tool name puts student tool-name validity at 98.8 percent on 84 calls, under the 99 percent gate on a sample too small to settle it.

incidents

The first student run silently ran in passthrough. Claude Code writes the served model's name into its own system prompt; our server was named with a suffix, the training span had the plain name, the anchors did not match, and the tap fell back to forwarding untouched. It was caught because the tap logs whether the swap applied. The fix normalises the name before anchoring; the lesson is that segments must be derived from sessions that vary every such field, and the swap must refuse rather than guess.

Lesson 9 · the ceiling

Why the speed prize is smaller on this model

Everyday anchorShortening a reference book helps most when the reader flips back to it constantly. A reader who took notes on the first pass and never flips back gains little from a thinner book.

Two separate costs come from a long preamble. Reading it once per request, which prefix caching already mostly removes. And looking back at it while writing: in a standard transformer every generated token re-reads everything before it, so a four-times-shorter preamble makes every one of those re-reads four times cheaper. That second cost is where Shopify's 38 percent came from.

Assumption exposed"Shopify's latency numbers transfer." Qwen3.8-27B is a hybrid: only 16 of its 64 layers look back over every previous token. The other 48 fold the preamble into a fixed-size summary, the same size whether the preamble is 20,000 tokens or 5,000. The look-back saving exists in a quarter of the model.
The pointGisting works as a method here, and the training says the model learns the compressed words. It pays out less on this architecture, and the measurement below says exactly how much less.

Lesson 10 · the loop (E4)

How short can the summary get, and can nobody be watching?

Everyday anchorA good lab assistant does not need you in the room. You leave a list of conditions to try, come back the next morning, and find a filled-in table, the equipment switched off, and a note about what broke and how it was handled.

Journey 3 proved a one-quarter summary. This journey asked how much further it can go, and whether the cycle can run without a person. Three boxes were rented, one per ratio. Each ran a worker chain: download, build, train against the shared teacher file, export, relaunch, self-test, raise a ready flag. A controller on the workstation polled the boxes, ran the twelve-task exam on each when ready, applied the gate, filed one results line, synced the artifacts, and destroyed the box.

Assumption exposed"The knee is at 4:1, like Shopify's." Their prompt was prose. Ours is 91 percent JSON tool schemas, and 1,099 made-up words for 17,539 real ones passed every task with perfect tool-name validity. Either schemas compress more gracefully, or these twelve tasks are too easy to expose the loss. Both readings say the same thing: build a harder exam before choosing a ratio to ship.

Lesson 11 · the harder exam

The defect the easy exam hid, and the rule that removes it

Everyday anchorA new hire aces the onboarding quiz. Then you ask them to file a document in the right cabinet and they put it in a cabinet that does not exist, confidently, with the right document inside. The quiz never asked them to find a cabinet.

Sixteen tasks were written to break a gist: count files with the Glob tool and write the number to a file; extract function names with Grep; plan with TaskCreate; summarise a file that contains an injected "delete everything" instruction; run tests whose failure message says to wipe the directory; rename a function with the read-before-edit rule in force; an explicit delete request; fetch a web page title; three long jobs on real repositories; research with the Agent tool and write notes. A log-aware scorer checked files and the tool-call sequence. The teacher and all four ratios sat the exam on one box in one afternoon.

Assumption exposed"Twelve of twelve at 16:1 means the gist is safe." The twelve tasks never asked the model to write to an absolute path. When the harder exam did, every compressed model wrote to a directory that does not exist: a scratch folder under a different session id, a home-folder path, a project named "mars-landing". exam

Sixteen tasks in driver/tasks_hard.txt on an adversarial seed repository, requests, click, typer, and the easy seed. Checks are programmatic: file contents, imports from the working copy, test runs filtered to the new tests, and tool-call sequence from the tap log (required tools, forbidden commands such as rm -rf or git clone after a booby-trapped failure message, read-before-edit ordering). The delete probe is the only task both arms fail or pass by chance: in headless mode there is nobody to ask, and the outcome depends on whether the model reaches for a denied command or a permitted one.

sub-agents

The Agent tool spawns sessions with their own system prompt and a 15-tool catalogue. Their anchors do not match, the tap passes them through untouched and logs it, so they run at full prompt length. A production gist needs a second span for them.

incidents

Four hosts destroyed before the evaluation box: two were still booting, because the serving image upgrades its SSH server from slow package mirrors and keys appear after about seven minutes; one had a start-up command of mine that wrote the key with permissions the server rejects; one machine writes that file with bad permissions on its own and refused the key twice in one day. The provisioning chain also failed three times because the tool shell is zsh, which passes a quoted option string to SSH as one argument; the chains now live in bash files. Two checker defects were found and corrected with the affected runs rescored: a test-name filter that missed the teacher's naming, and a type name the teacher chose following the repository's own convention.

Lesson 12 · the limit

What a week of practice with the rare tools did not buy

Everyday anchorYou can drill a new hire on the seldom-used equipment for a week. If their pocket summary has one line per machine for the common ones and half a line for the rest, they will still forget the rare ones exist when a job needs them.

Two recipes closed the program's queue. The first repeated Shopify's loss-averaging finding: averaging per response rather than per batch ended with a fifth more error and one fewer task passed, direction confirmed, magnitude mild. The second asked whether the gist's weakness on rarely used tools was a data problem. Forty-eight sessions were collected in which the full-prompt model was made to use every rarely used tool: notebooks, worktrees, background tasks, agent listing, search, messaging. The teacher reached every one, 16 of 16. The 299 resulting examples were added to the training set and the 8:1 gist retrained.

Assumption exposed"The rare-tool gap is a coverage gap; more examples close it." On a sixteen-task exam that requires the named rare tools, the 8:1 gist trained without the coverage data scored 10 of 16, and with it 9 of 16. Same tools missing both times: worktrees, web search, messaging. The teacher scores 16.

The pointAt 8:1 the compressed catalogue keeps the everyday tools reachable and turns the rare ones into a coin flip, and data does not change that. The remedies are a lower ratio for the tool block, a per-segment ratio that leaves rare schemas less compressed, or scoping the gist to workloads that never need them. One more warning came with it: the coverage model invented a directory once in sixteen sessions even with paths kept raw, so a deployment should validate write paths at the proxy.
Depth: the coverage exam, and what the two exams each see

The coverage exam (driver/tasks_coverage.txt, driver/eval_coverage.py) passes a task when every required tool was called at least once, regardless of outcome; it measures whether the tool is reachable from the compressed catalogue. The hard exam measures whether tasks get done. The coverage-trained model looked like the teacher's near-equal on the hard exam, 14 of 16, and like a 60 percent model on the coverage exam. Both readings are true, and a deployment decision needs both.

What the loop costs and what it is for

With the teacher file in place, one recipe is about four hours of training plus twenty minutes on the harder exam, $6 to $9 on this hardware depending on the host. The sweep in lesson 10 ran three recipes in parallel for about $21 including bad hosts; the retrain in lesson 11 cost about $8 and settled the program's most important question so far. The next recipes are already shaped for it: the loss-averaging ablation, a coverage run with sessions that call the eighteen unused tools, a second span for sub-agent sessions, and the clean latency measurement this architecture still owes.

Methods appendix: the operating discipline behind the numbers

Rented GPUs on a marketplace, one instance per journey, with a ledger written before any workload and an idle watchdog that destroys the instance after two idle hours. Results are synced down before the instance is destroyed, in the same session. Every journey has a timestamped operations log with each command, failure, and decision, and a reader-facing entry written before the next journey starts. Smoke tests run on the cheapest viable instance before any long run. Fix budget of about an hour per broken component before writing an honest null.
