Gisting for Coding Agents: Compressing Claude Code's Prompt into Learned Tokens on a Self-Hosted Hybrid-Attention Model

Eight experiment journeys, an unattended research loop, the rule that made the compressed agent match the original, what it buys in throughput, and the limit that data could not move.

Abstract

A coding agent sends a fixed preamble of behavioural rules and tool schemas on every model call. We test whether Shopify's gisting recipe, which replaces such a preamble with a small set of learned token embeddings trained by self-distillation with the model frozen, transfers to Claude Code 2.1.259 driving a self-hosted Qwen3.8-27B. Instrumenting the client with a logging proxy, we find the static preamble is 17,539 tokens after trimming, 91 percent of it tool schemas, and 73 percent of what the model reads on short sessions, falling to 0.44 integrated over long sessions and 0.18 at the deepest turns. We grow the model's embedding table, cache the teacher's top-32 log-probabilities once, train only the new rows for one epoch, and serve the result through a proxy substitution and a one-line template condition with no change to the client or the engine. On a twelve-task exam, ratios from 2:1 to 16:1 all match the teacher. On a sixteen-task exam built to stress rare tools, depth, rules, and adversarial content, every ratio drops to 11 or 12 of 16 against the teacher's 15, with a single shared cause: the working-directory path, session identifier included, had been compressed into the gist and the model wrote results to invented directories. Excluding verbatim-critical content from the span by pattern and retraining at 8:1 yields 16 of 16, equal to the teacher, reading 9,400 tokens per turn instead of 24,300. A clean benchmark with prefix caching on in both arms shows the gist's payoff on this hybrid-attention model is throughput rather than latency: 16 percent more requests per minute at saturation, 12 percent lower median latency, and a 39 percent lower p90 time to first token at moderate load, against Shopify's 38 percent latency gain on a standard transformer. Two further recipes bound the method: batch-level loss averaging beats per-response averaging as Shopify reported, mildly; and 299 targeted examples did not improve the gist's reach for rarely used tools, which stays near 60 percent of the teacher's on a coverage exam at 8:1, a capacity limit rather than a data shortage. The whole cycle from recipe to scored run executes unattended. Total cost across eight journeys was about $105 of rented GPU time.

1Introduction

An agentic coding tool such as Claude Code asks a language model what to do next at every step: read this file, run these tests, edit that function. Each request carries the same preamble: the rules the agent must follow and a JSON schema for every tool it can call. The model processes that preamble before producing anything, and in a standard transformer every generated token attends back over it. For a preamble of tens of thousands of tokens, that is a large fixed cost per turn.

Shopify's engineering team reported replacing a 6,000-token system prompt with 1,500 learned "gist" tokens, at a 4:1 ratio, with model weights frozen and only the new token embeddings trained. They measured a 38 percent drop in median end-to-end latency and 14 percent fewer GPUs on a production workload. Their post left several questions open for anyone with a different agent and a different model: how big the preamble share is in practice, whether the method survives long sessions where the preamble becomes a small fraction of context, what the failure modes look like, and how much a research loop around the method costs to run.

This paper reports an eight-journey program over five days that answers those questions for one concrete target: Claude Code 2.1.259 driving Qwen3.8-27B served by vLLM on a single 96 GB GPU. Two properties of the target make it a more demanding test than Shopify's. The preamble is dominated by JSON tool schemas rather than prose, and the model is a hybrid: only 16 of its 64 layers use full attention with a per-token cache over the prefix, which caps the decode-time saving that gisting exists to deliver.

The program's conclusions in one paragraph. Gisting transfers. The share of reading it can remove is 0.73 on short sessions and 0.44 on long ones. A gist trained in four hours matches the full-prompt model on both an easy and a hard exam, at 8:1, provided one rule holds: content that must be reproduced verbatim, paths, identifiers, dates, and names, stays outside the gist. Without that rule every ratio failed the same three tasks in the same way. On this hybrid model the payoff is 16 percent more throughput at saturation and a much shorter tail on time to first token, not the large single-request latency drop reported on a standard transformer. Its limit is reach: at 8:1 the gist makes rarely used tools a coin flip and more targeted data does not change that. The loop that produces and judges a gist runs without a person.

2Background

2.1Tokens, embeddings, and why the table is the doorway

A language model reads tokens, word pieces, each mapped by a lookup table, the embedding matrix, to a vector of a few thousand numbers. The model consumes only those vectors. Nothing requires the table to contain only real words: extra rows can be appended and their values chosen freely. Gisting is the observation that a few thousand such rows can be trained to carry the same information as the many thousands of real-word rows they replace, because natural text is a wasteful encoding of instructions.

2.2Self-distillation with frozen weights

The rows are trained by a matching game. The teacher is the model reading the full preamble; at each position of a logged reply it produces a distribution over the next token. The student is the same model reading the gist rows in place of the preamble. The training signal is the Kullback-Leibler divergence, a single number scoring how different two distributions are, summed over response positions. Gradient descent moves only the gist rows. Because no other weight changes, the model cannot drift elsewhere and the deliverable is a set of table rows plus tokenizer entries that any serving stack already understands. Shopify reported four recipe choices that mattered: initialising each gist row as the mean of the tokens it replaces, which cut initial loss seven-fold; measuring the compression knee rather than choosing it; averaging the loss over the batch rather than per response, which avoided hallucination; and precomputing the teacher, which cut a training run from 30 hours to 6.

2.3The target and its ceiling

Qwen3.8-27B is a 27-billion-parameter dense model with 64 layers, hidden size 5,120, untied input and output embeddings, and a 262k native context. Its configuration declares a full-attention interval of 4: 16 layers keep a per-token key-value cache over the prefix, and 48 are linear-attention layers that fold the prefix into a fixed-size state whatever its length. Gisting reduces two costs, prefill (reading the preamble once) and decode-time look-back (re-reading it for every generated token). Prefix caching in the engine already removes most prefill for an identical prefix. The look-back cost exists only in the 16 full-attention layers here, so the latency and memory saving from a shorter preamble should be roughly a quarter of what a standard model of the same size would show. The program treats that as a prediction to be measured, not assumed.

3System

Figure 1 shows the pieces. Claude Code speaks the Anthropic Messages API. vLLM 0.28 implements that API natively, so the client is pointed at the server with one environment variable and no translation layer. Between them sits a 260-line proxy, the tap, which forwards requests unchanged and logs each request, the reassembled reply, time to first token, and latency. The tap is the measurement instrument, later the place where the gist is substituted, and the A/B switch. The client is never modified.

The engine renders the tool array into the system message through the model's chat template, placing the tool block before the instruction text, after a one-line reasoning-effort preamble. Serving used the engine's defaults with three adjustments found necessary: a cap of 64 concurrent sequences, because the default of 1,024 exceeds the 674 state-space cache blocks that fit in 96 GB; a memory utilisation of 80 percent with 4,096-token prefill chunks during teacher caching, because full-vocabulary log-probabilities for one 8,192-token chunk need 8 GB; and a remap in the tap of the client's requested reasoning effort "high", which the model rejects, to "medium".

4Method

4.1Defining the span

The gistable unit is the token span that is byte-identical across sessions after the chat template renders it. We derive it by diffing the system text across logged sessions from several runs, so that fields that vary, the working-directory path, the git status block, the date, the served model name, are marked dynamic and kept as raw tokens. Static runs shorter than 32 tokens are also kept raw. After journey 5 a second rule was added: any line containing a path, a UUID, a date, or the served model name is dynamic by pattern regardless of whether it varied in the sample. Section 5.5 explains why. The resulting layout is three instruction segments and one tool block, 17,343 static tokens for the trimmed 27-tool catalogue.

4.2Growing the dictionary

The tokenizer receives <gist_0> to <gist_N-1> as added special tokens, one id each. The model had 243 spare embedding rows, so the input embedding is grown from 248,320 rows to the required count padded to 128, and each gist row is initialised as the mean of the k span tokens it replaces at ratio k:1. The output head is grown with zero rows, so a gist id can never win a vote; a logits processor in the engine additionally sets those ids to minus infinity. Across forty generation tests at temperatures 1.0 and 1.5, including prompts that asked for gist tokens by name, no gist id was ever emitted.

4.3Building examples

Each logged turn becomes one example: the teacher sequence (system text as the engine's adapter assembles it, tools, conversation, rendered through the template) plus the assistant reply; and the student sequence, identical except that each static segment is replaced by its gist string and the tool array is omitted. The conversion matches the engine's Anthropic adapter exactly, including that inline system messages are merged into the leading system block with no separator and tool results become role-tool messages. 1,494 examples came from 126 sessions.

4.4Caching the teacher

The teacher's opinion never changes, so it is computed once. The engine's completions endpoint returns, for every prompt position, the top-K tokens with log-probabilities. We keep the response positions at K=32; the retained mass is 0.999 on average and at the tenth percentile. The cache is 54 MB for 1,457 examples and took 4 hours 20 minutes, limited by the engine building a Python dictionary per position rather than by the GPU. With the cache, training needs only the student pass.

4.5Training

The model is frozen. A forward hook on the input embedding replaces rows for gist ids with a trainable tensor of shape (N, 5,120). Loss is KL from the teacher's renormalised top-32 to the student at each response position, summed over all response tokens in a step of eight examples and divided by their count, the batch-level reduction. Adam at learning rate 1e-3, one epoch, sequences capped at 30k tokens, gradient checkpointing. One step takes about 98 seconds on the 96 GB card; an epoch about four hours.

4.6Serving the gist

Two pieces, neither touching the engine's code. The tap in gist mode locates the anchor segments in the incoming system text, substitutes their gist strings, and prepends the tool-block gist, leaving the tools array in the request so the engine's tool-call parser stays active; it refuses to substitute and logs the fact when an anchor is missing. The chat template gains one condition: if the system message contains a gist token, the tool block is not rendered. Both arms of every evaluation run on the same server, since the gisted checkpoint has identical weights for every real token.

4.7Evaluation

Two exams. The easy exam is twelve tasks on a two-file repository with a deliberately failing test: add functions and tests, refactor, change an error type, write a README, explain without editing. The hard exam is sixteen tasks written to break a gist: file counts via Glob written to a file, function names via Grep, TaskCreate-planned work, summarising a file that contains an injected delete-everything instruction, running tests whose failure message says to wipe the directory, a rename under a read-before-edit rule, an explicit delete request, a WebFetch, three long jobs on requests and click, two on typer including one requiring the Agent tool, and three easy controls. A log-aware scorer checks files and the tool-call sequence. The gate for a run is task pass within ten points of the teacher, tool-name validity at or above 99 percent, no malformed calls, and no unswapped main-session turns.

The prediction of section 2.3 held. 5.7Loss reduction (E5)

The corrected 8:1 recipe was retrained with the KL averaged within each response and then across responses, instead of over all response tokens in the step. Held-out KL ended at 0.0107 against 0.0088 for batch-level; the hard exam scored 14 of 16 against 16, the real miss being the Agent task where the model researched but never wrote the notes file. No invented paths, no malformed calls. Shopify's direction holds; the magnitude here is mild, plausibly because our responses vary less in length than a customer-facing agent's. Batch-level remains the default.

5.8Coverage (E6)

Sixteen coverage tasks each require named rarely used tools (notebook editing, task tracking, background task output, agent listing, worktrees, cron listing, web search, sub-agents, skills, findings, messaging); a task passes when every required tool is called at least once. The teacher reached every tool, 16 of 16, using 21 distinct tools. Forty-eight such sessions yielded 299 examples, which were cached, merged with the base data, and used to retrain the corrected 8:1 rows (held-out KL 0.0188 to 0.0084).

6The research loop

Journeys 4 and 5 ran without a person between "recipe written" and "result recorded". The loop has six primitives, each a file in the repository.

  1. Recipe spec. One JSON line per run: ratio, learning rate, accumulation, epochs, sequence cap, initialisation, loss reduction, segment map, data, teacher cache.
  2. Worker chain on the rented box: lock file, disk check, download with three retries, delta build, cache check, training with out-of-memory retry at 0.8 times the cap and warm start from rows saved at each evaluation for the remaining epoch fraction, export, relaunch with two attempts, generation self-test, ready marker.
  3. Controller on the workstation: reloads the box list each round; on ready, runs the exam through the gist tap with that run's map, verifies no main-session turn ran unswapped, applies the gate, syncs artifacts, appends a results line, destroys the box; records a vanished box instead of polling it forever.
  4. Gate: task pass within ten points of the teacher, tool-name validity at least 0.99, zero malformed calls, zero unswapped turns.
  5. Versioning: the segment map ships with the trained rows; the tap refuses to swap when an anchor is missing.
  6. Results ledger: one line per run, the table this paper is built from.

On the ratio sweep the loop healed two out-of-memory runs, resumed one crash at step 65 of 135 from saved rows, replaced three bad hosts, and took each finished run from ready to destroyed in seven to eleven minutes. With the teacher cache in place a recipe costs four hours of training plus twenty minutes on the hard exam, $6 to $9 depending on the host. The whole hard-exam sweep across five arms ran on one box for about $4.

7Discussion

The knee is a content class, not a ratio. The easy exam said every ratio to 16:1 was safe; the hard exam said every ratio to 2:1 was broken in the same way. Neither statement was about compression strength. Content the model must reproduce exactly cannot be summarised at any ratio, and content that only shapes behaviour compresses gracefully, at least to 16:1 on this catalogue. Derive the span by pattern as well as by diff, and test with tasks that require verbatim reproduction.

Schemas compress better than prose, or the exams are still too easy. Shopify's knee at 4:1 was for prose. Our 16:1 on JSON schemas passed the easy exam and, once the path defect was removed, we have not yet seen a ratio fail on either exam. Both readings lead to the same action: an exam that exercises every tool, and long sessions where the gist is a small fraction of context.

What gisting buys on this architecture is throughput, not single-request latency. Prefix caching already removes most prefill for a static span and works on the hybrid model in the engine's align mode. The decode-time saving exists in 16 of 64 layers, so a lone session gains 3 percent. Under load the gist yields 16 percent more requests per minute and a 39 percent shorter p90 time to first token at moderate concurrency. The business case is therefore sessions per GPU and tail latency, weighed against the retraining cost on every client or catalogue change.

Sub-agents are a second span. The Agent tool spawns sessions with their own prompt and a 15-tool catalogue. The tap correctly refuses to swap them, so they run uncompressed. A deployment would need a gist per span, keyed by catalogue hash.

Rare-tool reach is a capacity limit at 8:1, not a data shortage. The training sessions called 9 of 27 tools. Adding 299 examples that exercise the other 18 lowered KL and left the coverage score unchanged, at about 60 percent of the teacher's. The compressed catalogue keeps the common tools reachable and makes the rare ones a coin flip. The remedies are a lower ratio for the tool block, a per-segment ratio that keeps rare schemas less compressed, or accepting the limit for workloads that never need those tools.

8Limitations and threats to validity

  • One model, one client version, one machine class. The span is a function of client version, plugin set, and MCP configuration; a different configuration is a different gist.
  • Small exams: twelve and sixteen tasks, four concurrent sessions, one run each. A pass count is a coarse instrument; the hard exam's task 7 is a defective probe and passed or failed by chance in both arms.
  • Two checker defects were found during the program and corrected with the affected runs rescored; the corrections are recorded in the results files rather than edited away.
  • Held-out KL is not comparable across ratios: each run filtered examples by its own sequence cap before splitting, and one resumed run drew a different subset. Task and tool columns are comparable.
  • The latency benchmark used one box, twelve sessions, and a fixed 200-token generation; production traffic with variable output lengths and higher concurrency may shift the numbers.
  • The coverage exam scores whether a tool was called, not whether the task succeeded; and the two gisted models were compared on one run each of sixteen tasks.
  • A residual invented-path failure at about one session in sixteen was observed after the fix; the tap does not yet validate write paths.
  • Provider incidents cost about $8 and two evaluation attempts; none affected a recorded result, but two boxes were destroyed prematurely and one host's logs were lost.

9Recommendations

  1. Adopt the verbatim-content rule as a hard constraint on span derivation: paths, identifiers, dates, and names are never inside a gist.
  2. Version the segment map with the trained rows, hash the rendered tool catalogue, and refuse to swap on any mismatch.
  3. Size the deployment case on throughput and tail latency, not median single-request latency: on a hybrid-attention model the gist yields about 16 percent more requests per minute at saturation and little for a lone session.
  4. Build the exam before the sweep. Tasks that require absolute paths, rare tools, rule-keeping, and adversarial content found in one afternoon what four training runs had missed.
  5. Do not claim catalogue-wide parity at 8:1. Sweep the tool-block ratio separately (2:1 or 4:1 for schemas, higher for instructions) against the coverage exam, or scope the gist to workloads that never need the rare tools.
  6. Validate absolute write paths at the tap against the session's working directory until path fidelity is shown to be stable.
  7. Treat sub-agent sessions as their own span.
