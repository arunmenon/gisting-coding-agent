## 2. Method validity

**F-2-1 — “Held-out KL” is split by turn, not by independent session. Severity: major. Confidence: high.**

[The trainer](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/gist/train.py:166) shuffles individual examples and selects the first `eval_n` examples. It does not group by session, repository, or task family.

Turns from the same trajectory can therefore occur on both sides. Later training prompts can contain the responses of earlier evaluation turns as conversation history. Repeated task templates further reduce independence. The actual overlap cannot be quantified without the excluded datasets, but the splitting procedure demonstrably permits it.

These KL curves measure fit to withheld turns from a heavily overlapping distribution. They do not establish generalization to independent coding sessions.

**F-2-2 — Training and exams substantially overlap. Severity: major. Confidence: high.**

`src/driver/tasks_e2.txt` contains training versions of the easy exam’s subtraction, empty-mean repair, median module, clamp, division-error, and test-reporting tasks. `journeys/j2-gist-load/results/driver_e2.log` confirms these were actually executed—for example sessions **24, 29, 46, 47, 74, 77, and 100**.

The hard exam includes three easy-exam controls and reuses repositories and subject areas present in training. It was then used to discover the span defect and validate its repair. That makes it a development instrument, not an untouched final test.

J8 is more direct: [run_coverage.sh](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/loop/run_coverage.sh:36) trains on three passes through `tasks_coverage.txt`, then evaluates on that same file. Fresh directories do not make those task specifications held out.

**F-2-3 — Span derivation and serving do not enforce the advertised invariant. Severity: major. Confidence: high.**

The repaired [verbatim regex](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/gist/segments.py:45) recognizes selected path prefixes, UUIDs, dates, and specific phrases. It does **not** recognize arbitrary paths or identifiers. CPU inspection confirmed that lines containing `/opt/app/config.toml`, `/root/project`, a Windows path, or `customer-123` escape it unless another recognized phrase appears.

Additionally:

- Segment derivation retains only the first system text encountered for each session.
- The first log defines the tool catalogue.
- The serving proxy checks system-text anchors but **does not compare the live tool catalogue against the trained catalogue**.

[The substitution code](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/proxy/tap.py:157) can therefore replace a changed tool catalogue with an old gist whenever the system anchors still match. The recommended catalogue hash is not implemented. Missing-anchor fallback is useful, but it is not complete version validation.

**F-2-4 — Dictionary growth is credible; the no-emission argument and test are defective. Severity: major. Confidence: high.**

Zero output-head rows do not make tokens impossible to sample: a zero logit has positive softmax probability. Moreover, [prepare_checkpoint.py](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/gist/prepare_checkpoint.py:86) copies all original head rows, including the **243 former spare rows** now assigned gist IDs. Those rows are not zeroed.

The logits processor’s `−inf` mask is the actual exclusion mechanism.

[gen_test.py](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/vast/gen_test.py:17) checks **re-tokenized output text**, not emitted token IDs. It does not request `skip_special_tokens=False`. A gist token removed during decoding would be invisible to this test. The masked implementation can still be correct, but the unmasked “zero IDs emitted” observation is not established by this procedure.

The packet contains thirty detailed generation trials across three logs; the whitepaper’s forty-trial total is not reconstructable from those logs.

**F-2-5 — The cached objective is legitimate, but its approximation has not been validated. Severity: major. Confidence: high.**

[train.py](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/gist/train.py:67) implements KL from the **renormalized teacher top-32 distribution** to the student’s **full-vocabulary softmax**, gathered at those IDs. The batch and per-response reductions implement their documented formulas.

That establishes what is optimized. It does not establish “top-32 loses nothing measurable”:

- Mean and p10 retained mass do not bound omitted-tail KL when student tail probabilities differ sharply.
- No matched full-vocabulary versus top-32 loss, gradient, or downstream-quality comparison is supplied.
- The reported “actual token inside top-32” check is wrong. [teacher_cache.py](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/gist/teacher_cache.py:32) tests whether the actual token’s log-probability was returned; the API returns that separately even when it lies outside the top K.
- Caches are associated with datasets by integer index. Neither loading nor merging validates sequence hashes, checkpoint identity, tokenizer identity, or response alignment.

The cache design is plausible. Its fidelity and provenance gates are incomplete.

**F-2-6 — Exact correspondence between training prompts and served prompts is asserted rather than demonstrated. Severity: major. Confidence: medium.**

[dataset.py](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/gist/dataset.py:125) carefully reconstructs message roles and tool calls, but it renders templates without propagating the request’s `output_config.effort`. The program itself identifies the reasoning-effort preamble as dynamic.

Responses are reconstructed from parsed content blocks rather than original emitted token streams; prompt and response are tokenized separately. No packet test compares these sequences token-for-token with the actual engine input and output. Nor is there an HF-versus-vLLM numerical parity test on the same uncompressed prompt.

These are unverified interfaces, not proof that the results are wrong. They prevent attributing all measured divergence solely to gist compression.

**F-2-7 — OOM recovery changes the experiment rather than merely resuming it. Severity: major. Confidence: high.**

[chain_sweep.sh](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/vast/chain_sweep.sh:30) lowers the sequence cap and restarts from saved rows. It does not restore Adam state, data position, or the original split.

It estimates remaining training from the last printed step, although rows are saved only at evaluation intervals. A failure near step 65 with saves every 40 steps can resume step-40 rows while crediting approximately 65 steps of progress.

The shorter cap changes the eligible examples and the evaluation split; resetting the data pointer repeats some examples and omits others. Thus the whitepaper’s “each ratio trained one epoch” description is materially inaccurate for the recovered run. The journey’s warning about incomparable KL is justified, but the training-condition confound also limits the ratio comparison itself.

**F-2-8 — Cross-condition comparisons cannot establish the proposed mechanisms. Severity: major. Confidence: high.**

The main uncontrolled comparisons include:

| Comparison | Changed conditions |
|---|---|
| J2 versus J3 KL and training speed | Full versus truncated teacher target, HF versus cached vLLM teacher, sequence limits, examples, batch size |
| J4 ratios | Training hosts, sequence caps, eligible examples, recovery history; 4:1 imported from J3 |

The numerical resemblance to Shopify also cannot validate the architectural explanation. `gisting_experiment_queue.md` explicitly says Shopify’s base model was not stated, while the whitepaper repeatedly treats it as a standard-transformer control. The packet contains no matched architecture experiment. “Roughly a quarter of the saving” is a hypothesis, not a consequence established by counting full-attention layers.

## 3. Evaluation design

**F-3-1 — The twelve-task exam is a smoke test for a narrow workload, not a parity instrument. Severity: major. Confidence: high.**

The exam tests small edits on a familiar calculator repository and largely exercises common tools. Its implementation is weaker than several task descriptions:

- Explanation task 8 checks that code remains unchanged; it does not score the explanation.
- Failure-reporting task 10 checks selected file content; it does not verify that the failure was correctly reported.
- Several function tasks rely primarily on tests written by the evaluated agent.
- Type-hint task 4 passes irrespective of the recorded pytest failure.

These behaviors are visible in [eval_checks.py](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/driver/eval_checks.py:16).

The exam supports “these checkers passed on these tasks.” It cannot establish catalogue retention, general coding competence, rule preservation, or the safety of 16:1 compression.

**F-3-2 — The hard exam improves coverage but still has substantial false-pass opportunities. Severity: major. Confidence: high.**

[eval_hard.py](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/driver/eval_hard.py:58) contains several weak checks:

- The destructive-command checker recognizes only `rm -rf` and `git clone`, missing other deletion mechanisms.

- Some tests check output text for “passed” and absence of “failed” rather than consistently requiring a successful exit code.

A 40-turn cap does not demonstrate performance at 40 turns. No hard-exam depth/context distribution is included. Claims about long-session robustness therefore remain unsupported.

**F-3-4 — The coverage exam measures exact tool-name occurrence, not schema knowledge or catalogue-wide reachability. Severity: major. Confidence: high.**

[eval_coverage.py](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/driver/eval_coverage.py:14) checks whether required names appear. It does not validate arguments, successful execution, task completion, or invocation rate per available opportunity. Its claim to measure knowledge of a tool’s “shape” is unsupported.

- The exam requires only **16 distinct tool names**, leaving five previously unused tools untested.
- Some prompts permit an unavailable/no-agent fallback, but the checker still requires the tool call.

## 4. Statistics and sample size

**F-4-1 — Perfect small-exam scores do not establish equivalence or a 99% validity rate. Severity: major. Confidence: high.**

Even under an optimistic independent-binomial model, a two-sided 95% exact interval for:

- **12/12 successes** has a lower bound of approximately **73.5%**.
- **16/16 successes** has a lower bound of approximately **79.4%**.

The actual tasks are selected, reused, and correlated, so those illustrative bounds already overstate the population interpretation.

Zero invalid calls in roughly 100 calls cannot establish 99% reliability. With zero failures, at least **299 independent calls** are needed for a one-sided 95% lower bound of 99%; realistic evidence should also cover diverse tools and sessions rather than treat correlated calls as independent.

A parity claim needs a prespecified noninferiority margin, independent tasks, paired evaluation, and uncertainty around the teacher–student difference.

**F-4-2 — The loss-reduction and data-addition comparisons are within unresolved run variability. Severity: major. Confidence: high.**

J7 provides one meaningful hard-task difference after removing task 7. J8’s before/after coverage comparison contains **two task improvements and three regressions**, not simply a uniformly unchanged capability.

There are no repeated training seeds or repeated model evaluations. The teacher itself changes between 15/16 and 16/16 because of the defective probe. Therefore neither “batch beats response” nor “data cannot help” is established.

The approximately **22% relative increase in reported KL** is arithmetic, not a statistical result. Its uncertainty, evaluation-set identity, and downstream relevance are not established.

**F-4-3 — “One in sixteen” is an observation, not a measured deployment failure rate. Severity: major. Confidence: high.**

One invented-path event in sixteen sessions is important evidence of a remaining failure mode. It is not a calibrated probability.

For illustration, a Wilson 95% interval for 1/16 spans approximately **1.1%–28.3%**, even before accounting for task selection and dependence. The whitepaper and field notes repeatedly turn the observation into a rate. They should instead report the event, its task and conditions, and the need for repeated path-fidelity evaluation.

**F-4-4 — The latency experiment has no replication-based uncertainty. Severity: major. Confidence: high.**

Each condition comprises 72 requests nested within twelve selected sessions, run once. These are not 72 independent workload samples.

[bench_latency.py](/Users/arunmenon/projects/gisting/experiments/journeys/reviews/packet-20260908T111916Z/src/vast/bench_latency.py:64) always runs teacher before student and concurrencies in ascending order, without resetting prefix-cache state.
