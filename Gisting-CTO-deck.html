Turning the prompt tax into GPU capacity

Compressing a coding agent’s fixed preamble into a handful of learned “gist” tokens — what it buys, what it costs, and what to fund next.

Arun Menon · arumenon@paypal.com
Claude Code → proxy → vLLM → Qwen3.8-27B (hybrid attention) · one GPU
Bottom line up front

The answer in four lines

The tax
At every step, the coding agent (Claude Code) re-sends the same fixed preamble to the model — ~17.5–21k tokens, over 90% tool schemas, about 0.72 of a short session.
The lever
Replace it with a few thousand learned tokens. Base model frozen; deployed in a proxy, no client or engine change.
The payoff
~16% more throughput at eight concurrent sessions — capacity per GPU, not faster single replies.
The caveat
A development study: the lever is real; the dollar-per-session number is not proven yet.

You can stop here. The rest is the evidence, the catch, and what it would take to bank the saving.

The cost lens

Why this is a total-cost question

For a self-hosted agent, serving cost is driven by how many tokens the model reads per turn, which caps how many sessions a GPU can carry. Three cost drivers — gisting acts on the first.

GPU capacity  ← gisting acts here
Token-bound. Fewer input tokens per turn → more concurrent sessions per GPU before latency degrades.
Engineering
One-time: build the proxy, the template, and the training loop. The loop is reusable across models.
Risk
Compressed rules are harder to audit; benefit is model-dependent. Managed, not eliminated.

The payoff

The saving shows up as capacity under load

Throughput rises with concurrency — and the gain grows as the service gets busier. A single reply is barely faster.

full prompt gist

For a shared internal agent service, this is sessions per GPU — the number that sets cost. One replay; direction, not precision.

The catch · architecture

Why it’s capacity, not speed

This model uses full attention in only 16 of its 64 layers. A shorter prompt saves decode work only there — so the win is more sessions in parallel, not a faster individual answer.

■ full-attention layers (benefit)    ■ linear-attention layers (fixed-size state). The benefit is architecture-dependent: a different model shifts it.

Honest ledger

What’s proven, what isn’t

Established here
  • Equal task scores on our suites, every ratio.
  • Half-to-two-thirds fewer tokens read per turn.
  • Throughput rises under load; the fix removes the path failure.
  • The tooling works end to end.
Not yet
  • Generalisation on unseen, held-out work.
  • A saturation test → a real sessions-per-GPU / $ number.
  • The cause of the serving gain (a hypothesis, not proven).
  • Rare-tool reach (left unscored by harness faults).
  • Audit guarantees that compressed rules still bind.

An independent adversarial review of the whole program was run and folded into the writeup.

The ask

From “real lever” to a number you can budget

1 · Validate
A held-out eval with paired, repeated runs. Answers: is the parity real beyond our own tasks?
2 · Quantify
A saturation test under sustained load. Converts “throughput direction” into sessions per GPU and a cost per session.
3 · Pilot
A guarded rollout with explicit rule-audit and write-target checks at the serving boundary.

Bounded effort: a single GPU over days, not a new research program — the loop and serving path already exist.

Decision

The lever is real and cheap to prototype

Fund a short validation — eval + saturation — before any production commitment.

The tooling exists, the risk is contained, and the upside is GPU capacity that compounds under load. What’s missing is a validated number, and that is days of work away, not months.
